## 1. 대규모 푸시 발송 최적화: 가상 스레드 vs 콜백 패턴

### 1-1. 현재 구조 요약

```
FcmOrchestrator.sendToCluster()                      [호출 스레드: 요청 스레드 또는 스케줄러 스레드]
 ├─ findTokensByCluster(cluster)                      클러스터의 토큰 전체 조회
 ├─ splitIntoBatches(tokens, 400)                     400개 단위로 분할
 └─ for each batch
     ├─ markBatchAsSendingAndSave(batch)              DB: IN_PROGRESS bulk update (배치마다 트랜잭션 1회)
     ├─ buildMessages(...)
     └─ FcmPushService.sendBatchAsync(messages, cb)
          └─ FirebaseMessaging.sendEachAsync(messages)
               └─ 메시지 400개 각각 callAsync(app) ──▶ fcm-default 풀에 400개 태스크 제출
                                                      (각 태스크가 HTTP 요청 1건을 "블로킹"으로 수행)
          └─ ApiFutures.addCallback(future, cb, fcmCallbackExecutor)
               └─ 400건이 모두 끝나면 fcm-callback 풀에서
                  processPushResult() 실행                DB: 토큰 상태 bulk update + 카운트 증가
```

스레드별로 나눠 보면 블로킹되는 주체는 다음과 같습니다.

| 스레드 | 하는 일 | 블로킹 여부 |
|---|---|---|
| 호출 스레드 (웹훅 요청 / 스케줄러) | 배치마다 DB 업데이트 후 태스크 400개를 큐에 넣고 콜백을 등록 | DB 업데이트 동안만 블로킹. **FCM 응답은 기다리지 않고 즉시 반환** |
| `fcm-default` 워커 | 큐에서 메시지 1건을 꺼내 HTTP 요청 후 응답 대기 | **자기 메시지 1건의 RTT 동안 블로킹** |
| `fcm-callback` | 400건이 모두 끝났다는 이벤트를 받아 결과를 DB에 반영 | DB 작업 동안 블로킹 |

"400건이 모두 끝나면"은 **콜백이 실행되는 시점**을 뜻합니다. 그 시점까지 블로킹되는 스레드는 없습니다.
`allAsList` 는 완료된 개수만 세고, 마지막 400번째 메시지를 처리한 워커가 future를 완료시키면 콜백이 `fcm-callback` 으로 넘어갑니다.

스레드 풀 설정(`config/fcm.yaml`)은 다음과 같습니다.


| 풀              | 용도                                                         | core | max | queue  |
| -------------- | ---------------------------------------------------------- | ---- | --- | ------ |
| `fcm-default`  | Firebase SDK의 `ThreadManager` 실행기. **메시지 1건당 태스크 1개**가 실행됨 | 32   | 128 | 50,000 |
| `fcm-callback` | 배치 400건이 끝난 뒤 결과를 DB에 반영하는 콜백 실행                           | 8    | 32  | 500    |
| HikariCP       | DB 커넥션                                                     | -    | 10  | -      |


### 1-2. 핵심 발견: 현재 "콜백 패턴"은 실제로 논블로킹이 아니다

`sendEachAsync` 라는 이름과 `ApiFutureCallback` 사용 때문에 전체 경로가 논블로킹처럼 보이지만,
firebase-admin 9.4.0 소스를 확인해 보면 실제 동작은 다릅니다.

**① 메시지마다 스레드 풀 태스크를 하나씩 만든다** (`FirebaseMessaging.sendEachOpAsync`)

```java
for (Message message : immutableMessages) {
  // Make async send calls per message
  ApiFuture<SendResponse> messageId = sendOpForSendResponse(message, dryRun).callAsync(app);
  list.add(messageId);
}
return ApiFutures.transform(ApiFutures.allAsList(list), BatchResponseImpl::new, directExecutor());
```

`callAsync(app)` 는 `ImplFirebaseTrampolines.submitCallable(app, this)` 를 호출하며,
이 메서드는 `FcmInitializer` 가 `ThreadManager` 로 주입한 `fcm-default` 풀에 태스크를 제출합니다.

**② 각 태스크는 HTTP 응답이 올 때까지 스레드를 붙잡고 기다린다** (`ApacheHttp2Request.execute`)

```java
final Future<...> responseFuture = httpAsyncClient.execute(...);   // HTTP/2 비동기 클라이언트에 요청
...
final Message<HttpResponse, ApacheHttp2Entity> response = responseFuture.get();  // ← 블로킹 대기
```

9.4.0부터 전송 계층은 Apache HttpClient 5 기반의 **HTTP/2 비동기 클라이언트**로 바뀌었습니다.
그러나 google-http-client의 `LowLevelHttpRequest.execute()` 계약이 동기식이기 때문에,
SDK는 비동기 클라이언트에 요청을 보낸 직후 `future.get()` 으로 응답을 기다립니다.

**결론적으로 현재 구조는 "메시지 1건 = 플랫폼 스레드 1개가 RTT 동안 블로킹"** 입니다.
`ApiFutureCallback` 은 400건이 **모두 끝난 뒤의 후처리**만 비동기로 넘길 뿐이고,
실제 네트워크 대기 구간은 `fcm-default` 풀의 스레드 수에 의해 동시성이 제한됩니다.

이 사실이 가상 스레드 논의의 출발점입니다. 가상 스레드가 효과를 내는 조건은
"스레드 1개가 요청 1건의 응답을 블로킹으로 기다리는 구조여서, 동시에 진행되는 요청 수가 스레드 수를 넘을 수 없는 상황"이고,
현재 구조가 바로 그 상황입니다.

여기서 블로킹은 **동시성이 없다는 뜻이 아닙니다.** 블로킹은 호출한 스레드 하나만 멈추게 하고, 나머지 스레드는 OS가 계속 실행합니다.
워커 32개가 각각 자기 요청을 기다리고 있다면 FCM으로 나간 요청 32건이 동시에 진행 중이므로 동시성은 32입니다.
동시성이 정말 없는 경우는 스레드 하나가 `send()` 를 반복문으로 호출해 한 건씩 기다리는 구조(동시성 1)입니다.

참고로 HTTP 계층의 상한은 다음과 같이 충분히 넉넉합니다(`ApacheHttp2Transport`).

```java
.setMaxConnTotal(200)
.setMaxConnPerRoute(100)
// Set maxConcurrentStreams to 100 to match the concurrent stream limit of the FCM backend.
.setH2Config(H2Config.custom().setMaxConcurrentStreams(100).build())
```

즉 커넥션 100개 × 스트림 100개 = 이론상 **최대 10,000건을 동시에 전송할 수 있는 전송 계층** 위에서,
스레드 32개가 병목을 만들고 있는 구조입니다.

### 1-3. 핵심 발견: 유효 동시성은 128이 아니라 32다

`ThreadPoolExecutor` 는 다음 순서로 동작합니다.

1. 실행 중인 스레드가 `core` 보다 적으면 새 스레드를 만든다.
2. `core` 에 도달하면 **큐에 먼저 적재한다.**
3. **큐가 가득 찬 경우에만** `max` 까지 스레드를 늘린다.
4. `max` 에도 도달하고 큐도 가득 차면 `RejectedExecutionException` (기본 `AbortPolicy`)을 던진다.

`fcm-default` 는 `core=32`, `queue=50,000` 이므로, 대기 중인 태스크가 5만 건을 넘기 전까지는
**스레드가 32개에서 늘어나지 않습니다.** `max=128` 은 평상시에는 사실상 동작하지 않는 설정입니다.

따라서 현재 처리량의 상한은 다음 식으로 결정됩니다.

```
처리량(건/초) ≈ 유효 스레드 수 / 메시지 1건의 평균 RTT(초) = 32 / RTT
```

### 1-4. 잠재 위험: 큐 초과 시 중복 발송 가능성

이 항목은 코드 구조에서 추론한 위험이며, 운영 환경에서 재현한 사례는 아닙니다.

**발생 조건 추정**

- 오케스트레이터는 배치마다 DB 업데이트 1회(수십 ms)만 하고 곧바로 다음 배치 400건을 제출합니다.
제출 속도는 초당 수천\~1만 건 수준입니다.
- 소비 속도는 `32 / RTT` 로, RTT가 80ms라면 초당 약 400건입니다.
- 따라서 단일 발송 대상이 대략 **5만 건 + α** 를 넘으면 큐가 가득 차고, 스레드가 128개까지 늘어난 뒤에도
제출이 계속되면 `RejectedExecutionException` 이 발생할 수 있습니다.

400은 배치 크기일 뿐이고 큐가 가득 차는 기준이 아닙니다. 거절은 큐(50,000)가 가득 차고 스레드도 max(128)까지 늘어난 뒤에야 발생합니다.

**거절이 발생하는 경로 (소스로 확인)**

```
FcmPushService.sendBatchAsync
 └─ ApiFutures.addCallback( sendEachAsync(messages), callback, executor )
                            └─ ① Java는 인자를 먼저 평가하므로 sendEachAsync 가 먼저 실행됨
                               └─ for (message : 400개)
                                    callAsync(app)
                                     └─ FirebaseApp.submit()           ← 예외를 잡지 않음
                                         └─ executor.submit(command)   ← 여기서 RejectedExecutionException
```

예외가 호출 스레드에서 동기적으로 던져지므로 `ApiFutures.addCallback(...)` 은 **호출되지 않습니다.**
"예외가 나도 콜백은 등록된다"가 아니라, 콜백을 등록하는 줄에 도달하지 못합니다.

**발생 시 영향** (배치 N의 k번째 메시지에서 거절된 경우)

| 대상 | 상태 |
|---|---|
| 배치 1 ~ N-1 | 정상 제출 → 전송되고 결과도 반영됨 |
| 배치 N의 1 ~ k-1번째 메시지 | **이미 큐에 들어갔으므로 실제로 전송됨.** 그러나 콜백이 없어 결과가 DB에 반영되지 않음 |
| 배치 N의 k ~ 400번째 메시지 | 제출되지 않음 → 전송 안 됨 |
| 배치 N+1 이후 | 예외가 `sendToCluster` 루프를 빠져나가므로 발송도, `IN_PROGRESS` 표시도 안 됨 (`PENDING` 그대로) |
| 이후 클러스터들 | `dispatchClusters` 의 `forEach` 도 중단되어 발송 안 됨 |

예외는 `sendToCluster → dispatchClusters → WebhookOrchestrator.processWebhook → 웹훅 컨트롤러` 로 전파되어 크롤링 서버가 오류 응답을 받습니다.
`ClubEvent` 와 `PushCluster` 는 이미 커밋된 상태입니다.

10분 뒤 `PushPollingPublisherScheduler` 가 배치 N(`IN_PROGRESS` stale)과 배치 N+1 이후(`PENDING` stale)를 모두 재발송합니다.
결과적으로 **배치 N의 1 ~ k-1번째 사용자는 같은 알림을 두 번** 받고, 나머지는 최소 10분 늦게 받습니다.
크롤링 서버가 오류 응답을 받고 웹훅을 재전송한다면 클러스터가 중복 생성될 수도 있습니다(크롤러 코드는 확인하지 않았습니다).

이 문제는 §1-12의 리팩토링(세마포어 + 용량 불변식)으로 구조적으로 막았습니다.

현재 구독자 규모에서는 발생 가능성이 낮지만, "대규모 발송"을 논의한다면 반드시 짚어야 하는 지점입니다.

### 1-5. 가상 스레드를 도입한다면: 세 가지 선택지

먼저 짚어야 할 점이 있습니다. **`spring.threads.virtual.enabled=true` 만으로는 FCM 발송이 빨라지지 않습니다.**
이 설정은 Tomcat 요청 스레드, `@Async` 기본 실행기, `@Scheduled` 실행기에 적용되며,
직접 생성한 `ThreadPoolTaskExecutor` 빈(`fcmDefaultExecutor`, `fcmCallbackExecutor`)에는 적용되지 않습니다.
또한 호출 스레드만 가상 스레드로 바꿔도, SDK는 여전히 `ThreadManager` 의 풀(32개)로 메시지를 흩뿌립니다.
**병목을 해소하는 지점은 `ThreadManager.getExecutor()` 가 반환하는 실행기입니다.**

#### 선택지 A. 콜백 패턴 유지 + SDK 실행기만 가상 스레드로 교체 (변경 최소)

```java
// FcmInitializer (개념 코드, 적용하지 않음)
private final ExecutorService fcmVirtualExecutor =
    Executors.newThreadPerTaskExecutor(Thread.ofVirtual().name("fcm-vt-", 0).factory());

@Override
protected ExecutorService getExecutor(FirebaseApp app) {
    return fcmVirtualExecutor;
}
```

- 메시지 1건당 가상 스레드 1개가 생성되고, `responseFuture.get()` 에서 블로킹되면 **캐리어 스레드를 반납하고 park** 됩니다.
- `FcmOrchestrator` / `FcmPushService` / 콜백 코드는 그대로 둘 수 있습니다.
- 대신 **동시성 상한이 사라지므로** 별도의 제한 장치(세마포어)가 필요합니다(1-9 참고).

#### 선택지 B. 동기 스타일로 재작성 (배치당 가상 스레드 1개 + 결과 처리를 같은 흐름에서 수행)

```java
// 개념 코드, 적용하지 않음
try (var scope = Executors.newVirtualThreadPerTaskExecutor()) {
    for (List<PushClusterToken> batch : batches) {
        permits.acquire();                       // 동시 배치 수 제한
        scope.submit(() -> {
            try {
                BatchResponse res = FirebaseMessaging.getInstance().sendEach(messagesOf(batch));
                fcmPushResultService.processPushResult(clusterId, batch, res);
            } catch (FirebaseMessagingException e) {
                fcmPushResultService.markBatchAsRetryPendingAndSave(batch);
            } finally {
                permits.release();
            }
        });
    }
}   // close() 가 모든 배치 완료까지 대기 → "발송 완료 시점"이 코드에 명확히 드러남
```

- `sendEach` 는 내부적으로 `sendEachOpAsync(...).get()` 이므로, **선택지 A(SDK 실행기 교체)와 함께 적용해야** 효과가 있습니다.
B만 단독으로 적용하면 코드 모양만 바뀌고 동시성은 여전히 32입니다.
- 장점은 성능보다 **가독성과 오류 처리**입니다. 예외가 `try/catch` 로 자연스럽게 전파되고,
"클러스터 발송 전체가 끝나는 시점"을 `close()` 로 알 수 있어 클러스터 상태 전이를 한 곳에서 처리할 수 있습니다.

#### 선택지 C. SDK를 우회하고 FCM HTTP v1 API를 진짜 논블로킹으로 호출

- `java.net.http.HttpClient.sendAsync()` (HTTP/2) 또는 WebClient로 `messages:send` 를 직접 호출합니다.
- 소수의 스레드로 수천 건을 동시에 처리할 수 있어 자원 효율은 가장 좋습니다.
- 대신 OAuth2 액세스 토큰 갱신, 에러 응답 → `MessagingErrorCode` 매핑, 재시도 헤더 처리 등을
**직접 구현하고 유지보수해야** 합니다. 현재 규모에서는 비용 대비 이득이 작습니다.

### 1-6. 콜백 패턴 vs 가상 스레드 비교 (장단점 / 트레이드오프)

여기서 "콜백 패턴"은 현재 구조(플랫폼 스레드 풀 + `ApiFutureCallback`)를,
"가상 스레드"는 선택지 A 또는 A+B를 의미합니다.


| 관점       | 콜백 패턴 (현재)                                                       | 가상 스레드 (A / A+B)                                                  |
| -------- | ---------------------------------------------------------------- | ----------------------------------------------------------------- |
| 동시성 상한   | 풀 크기(유효 32)에 묶임                                                  | 스레드 수가 상한이 아님. 세마포어로 **의도적으로** 정한 값이 상한                           |
| 메모리      | 플랫폼 스레드 1개당 스택 1MB 예약(실사용 수백 KB). 수백 개 이상은 부담                    | 가상 스레드 1개당 수 KB(힙에 스택 청크 저장). 수만 개도 가능                            |
| 백프레셔     | 큐 용량 + `RejectedExecutionException` 이라는 **거친** 방식. 1-4의 중복 발송 위험 | 기본값은 백프레셔 없음. 세마포어를 **직접** 설계해야 함                                 |
| 코드 가독성   | 콜백 중첩, 성공/실패 경로 분리, 완료 시점 추적이 어려움                                | (B 적용 시) 순차 코드, `try/catch`, 완료 시점이 명확                            |
| 예외 전파    | 콜백 안에서 삼켜지기 쉬움. `onFailure` 누락 시 조용히 유실                          | 호출 스택을 따라 자연스럽게 전파                                                |
| 관측성      | `ExecutorServiceMetrics` 로 active/queued/pool size를 바로 볼 수 있음    | `ThreadPoolExecutor` 가 아니므로 기존 메트릭이 사라짐. in-flight 게이지를 직접 만들어야 함 |
| MDC 전파   | `MdcTaskDecorator` 로 이미 해결됨                                      | 새 실행기에 MDC 래핑을 다시 적용해야 함                                          |
| 피닝 위험    | 없음                                                               | Java 21에서 `synchronized` 블록 안의 블로킹은 캐리어를 붙잡음(JEP 491은 Java 24부터)  |
| 다운스트림 보호 | 풀 크기가 곧 DB/FCM 보호 장치 역할을 우연히 수행                                  | 무제한 동시성이 DB 커넥션(10개)과 FCM 쿼터를 한 번에 압박할 수 있음                       |
| 튜닝 난이도   | core/max/queue 3개 값의 상호작용을 이해해야 함(1-3처럼 오해하기 쉬움)                 | 동시 요청 수 1개 값만 정하면 됨                                               |
| 변경 범위    | 없음                                                               | A: `FcmInitializer` + 세마포어 / A+B: 오케스트레이터 재작성                     |


**트레이드오프의 핵심**은 다음 한 문장으로 정리됩니다.

> 가상 스레드는 "스레드 수 = 동시성 상한"이라는 제약을 없애 주지만, 그 제약이 **우연히 수행하던 보호 역할**
> (DB 커넥션 보호, FCM 쿼터 보호, 메모리 보호)도 함께 없앤다. 따라서 가상 스레드 도입은
> "스레드 풀 튜닝"을 "명시적 동시성 제한(세마포어) 설계"로 바꾸는 작업이다.

그리고 한 가지를 더 짚어야 공정한 비교가 됩니다.
**현재 문제의 상당 부분은 가상 스레드 없이도 `fcm-default` 의 core를 200\~500으로 올리면 해결됩니다.**
플랫폼 스레드 500개는 실사용 메모리 기준 수십\~100MB 수준이라 서버 한 대가 감당할 수 있습니다.
가상 스레드가 확실히 우위를 갖는 영역은 (1) 동시성을 수천 이상으로 올려야 할 때,
(2) 큐 크기와 풀 크기의 상호작용을 신경 쓰고 싶지 않을 때, (3) B처럼 코드를 동기 스타일로 단순화하고 싶을 때입니다.

### 1-7. 성능 수치 비교 (모델 계산)

**가정**

- 메시지 1건의 RTT(서버 → FCM → 응답)는 50ms / 100ms / 200ms 세 가지 경우로 나눠 계산합니다.
실제 값은 1-8의 실측으로 확인해야 합니다.
- FCM HTTP v1의 기본 전송 쿼터는 프로젝트당 **분당 600,000건(초당 10,000건)** 입니다.
이 값을 넘으면 `QUOTA_EXCEEDED` 가 발생하고, 현재 코드는 재시도 대기 시간을 2배로 늘립니다.
- DB 결과 반영(배치 400건 bulk update)은 배치당 20\~50ms로 가정하며, 콜백 풀에서 병렬로 처리되므로
전송 구간보다 병목이 되지 않는다고 봅니다(아래 별도 검토 참고).

**처리량(건/초) = 동시성 ÷ RTT, 단 FCM 쿼터 10,000건/초로 상한 적용**


| 구성                         | 유효 동시성 | RTT 50ms       | RTT 100ms      | RTT 200ms |
| -------------------------- | ------ | -------------- | -------------- | --------- |
| 현재 (core 32, queue 50,000) | 32     | 640            | 320            | 160       |
| 플랫폼 풀 core 128로 상향         | 128    | 2,560          | 1,280          | 640       |
| 플랫폼 풀 core 500으로 상향        | 500    | 10,000 (쿼터 상한) | 5,000          | 2,500     |
| 가상 스레드 + 세마포어 500          | 500    | 10,000 (쿼터 상한) | 5,000          | 2,500     |
| 가상 스레드 + 세마포어 1,000        | 1,000  | 10,000 (쿼터 상한) | 10,000 (쿼터 상한) | 5,000     |


**10만 건 발송 완료까지 걸리는 시간(전송 구간만)**


| 구성                   | RTT 50ms | RTT 100ms       | RTT 200ms        |
| -------------------- | -------- | --------------- | ---------------- |
| 현재 (32)              | 약 156초   | 약 313초 (5분 13초) | 약 625초 (10분 25초) |
| 플랫폼 128              | 약 39초    | 약 78초           | 약 156초           |
| 플랫폼 500 / 가상 스레드 500 | 약 10초    | 약 20초           | 약 40초            |
| 가상 스레드 1,000         | 약 10초    | 약 10초           | 약 20초            |


위 표에서 읽을 수 있는 점은 다음과 같습니다.

1. **동시성이 같다면 가상 스레드와 플랫폼 스레드의 처리량은 같습니다.** 가상 스레드는 스레드를 빠르게 만드는 기술이 아니라,
 많은 스레드를 싸게 만드는 기술입니다.
2. 동시성을 500 이상으로 올리면 곧 **FCM 쿼터(초당 10,000건)가 새로운 상한**이 됩니다. 그 이상 올리는 것은 의미가 없고,
 오히려 `QUOTA_EXCEEDED` 로 재시도 비용만 늘어납니다.
3. 현재 구조에서 RTT 200ms 환경이면 10만 건 발송에 10분 이상 걸립니다. 이 경우 `stale-threshold-minutes: 10` 과 겹쳐서
 **아직 큐에서 대기 중인 토큰이 stale로 오판되어 재발송될 가능성**이 생깁니다
 (`markBatchAsSendingAndSave` 로 `processedTime` 을 먼저 찍어 두기 때문입니다).

**메모리 비교 (동시 실행 단위 기준, 추정)**


| 구성            | 동시 실행 단위 | 스레드 스택 메모리 추정                     |
| ------------- | -------- | --------------------------------- |
| 플랫폼 스레드 500   | 500      | 예약 500MB(가상 메모리), 실사용 약 50\~125MB |
| 가상 스레드 500    | 500      | 약 1\~10MB (park 상태의 스택 청크)        |
| 가상 스레드 10,000 | 10,000   | 약 20\~200MB                       |


**DB 결과 반영 구간 검토**

- 10만 건 = 250배치 → 콜백 250회, 각 콜백은 트랜잭션 1회에서 bulk update(400행) + 토큰 soft delete + 카운트 증가를 수행합니다.
- 콜백 풀 최대 32개가 HikariCP 커넥션 10개를 두고 경쟁합니다. 배치당 50ms라면 초당 약 200배치(8만 건)를 반영할 수 있어
전송 구간보다 빠릅니다.
- **주의:** 콜백 실행기까지 가상 스레드로 바꾸면 250개 트랜잭션이 동시에 커넥션 10개를 요청하게 되고,
`connection-timeout: 30000` 을 넘기면 결과 반영이 실패합니다. **콜백 쪽은 플랫폼 풀을 유지하거나,
세마포어를 커넥션 수 이하로 설정해야** 합니다.

### 1-8. 실측 계획 (dryRun 기반)

FCM은 `validate_only`(SDK의 `dryRun=true`) 옵션을 제공합니다. 실제 FCM 서버까지 요청이 가지만 기기로 전달되지 않으므로,
**실제 네트워크 RTT를 포함한 처리량을 사용자에게 알림을 보내지 않고 측정**할 수 있습니다.

1. 측정용 토큰 목록을 준비합니다. 유효한 토큰일 필요는 없지만, 형식이 잘못된 토큰은 `INVALID_ARGUMENT` 로 빠르게 반환되어
 RTT가 실제보다 짧게 측정될 수 있으므로 **운영과 같은 형식의 토큰**을 사용합니다.
2. 운영과 같은 리전(EC2)에서 `sendEachAsync(messages, true)` 로 400건 배치를 N회 전송하는 하네스를 만듭니다.
3. 아래 구성을 각각 3회 이상 측정합니다.
   - 현재 설정 (core 32)
   - 플랫폼 core 128 / 500
   - 가상 스레드 + 세마포어 200 / 500 / 1,000
4. 수집 지표
   - 총 소요 시간, 처리량(건/초), 메시지별 RTT p50/p95/p99
   - JVM 힙, 스레드 수(`jvm.threads.live`), GC 일시정지
   - 가상 스레드 피닝: Java 21에서는 `-Djdk.tracePinnedThreads=full` 또는 JFR `jdk.VirtualThreadPinned` 이벤트
   - `QUOTA_EXCEEDED` 발생 여부
5. 결과를 1-7의 표에 "실측" 열로 추가해 모델값과 비교합니다.

주의: dryRun 요청도 FCM 쿼터에 포함될 수 있으므로, **운영 발송 시간대(평일 9\~21시)를 피해서** 측정합니다.

### 1-9. 도입 시 주의사항 체크리스트

1. **동시성 제한은 필수입니다.** SDK 실행기를 가상 스레드로 바꿀 때 `Semaphore` 로 in-flight 요청 수를 제한합니다.
 제출 측(오케스트레이터)에서 `acquire` 하고, 콜백 완료 시 `release` 하면 **자연스러운 백프레셔**가 생겨
 1-4의 큐 초과 문제도 함께 사라집니다.
2. **피닝 점검 (Java 21):** `synchronized` 블록 안에서 블로킹하면 캐리어 스레드가 묶입니다.
 이번에 확인한 범위에서는 문제가 없었습니다.
   - httpcore5 5.3.6 `BasicFuture.get()`: `ReentrantLock` + `Condition.await()` 사용 → 피닝 없음 (바이트코드로 확인)
   - mysql-connector-j 9.x: 내부 락을 `ReentrantLock` 으로 전환한 버전
   - 그 밖의 라이브러리(로깅 appender, Google 인증 토큰 갱신 등)는 실측 시 JFR로 확인해야 합니다.
   - 근본 해결은 Java 24 이상(JEP 491: `synchronized` 피닝 제거)으로 올리는 것입니다.
3. **메트릭 대체:** `fcm_default_executor` 메트릭이 사라지므로 `fcm.inflight` 게이지(세마포어 사용량)와
 전송 지연 타이머를 추가해야 Grafana 대시보드가 유지됩니다.
4. **MDC 전파:** 새 실행기에도 `MdcTaskDecorator` 와 같은 래핑을 적용해야 traceId가 로그에 남습니다.
5. **종료 처리:** 현재는 `setWaitForTasksToCompleteOnShutdown(true)` 로 종료 시 대기합니다.
 가상 스레드 실행기도 `@PreDestroy` 에서 `shutdown()` + `awaitTermination()` 을 호출해야 배포 중 발송이 유실되지 않습니다.
6. **ThreadLocal 사용 점검:** 가상 스레드는 풀링하지 않으므로, ThreadLocal에 무거운 객체를 캐싱하는 코드가 있다면
 스레드마다 새로 만들어져 오히려 비효율적입니다.
7. **stale 임계값 재검토:** 발송이 빨라지면 문제가 줄어들지만, 반대로 대규모 발송이 10분을 넘을 수 있는 구조라면
 `processedTime` 을 "큐 적재 시점"이 아니라 "실제 전송 시작 시점"에 찍는 방식도 검토할 만합니다.

### 1-10. 결론과 권장안


| 단계  | 조치                                                                                    | 기대 효과                                 | 변경 규모                         |
| --- | ------------------------------------------------------------------------------------- | ------------------------------------- | ----------------------------- |
| 0단계 | `fcm-default` 를 `core=max` 로 맞추고 큐를 작게(예: core 200, queue 1,000) + `CallerRunsPolicy` | 유효 동시성 32 → 200, 거절 대신 호출 스레드가 속도를 늦춤 | 설정 변경                         |
| 1단계 | SDK `ThreadManager` 실행기를 가상 스레드로 교체 + 세마포어(500)                                       | 동시성 500, 쿼터 근처까지 처리량 확보, 큐 초과 위험 제거   | `FcmInitializer` + 오케스트레이터 일부 |
| 2단계 | 오케스트레이터를 동기 스타일(B)로 재작성                                                               | 가독성, 예외 처리, 클러스터 완료 시점 명확화            | 오케스트레이터 재작성                   |
| 보류  | FCM HTTP v1 직접 호출(C)                                                                  | 자원 효율 최고                              | 인증·에러 매핑 직접 구현                |


**권장:** 현재 구독자 규모에서는 0단계만으로도 처리량이 약 6배(32 → 200) 늘어납니다.
어느 단계든 **1-8의 dryRun 실측으로 RTT를 먼저 확인한 뒤** 동시성 값을 정해야 합니다.

> **결론 갱신:** 이후 논의(§1-11)에서 "풀 크기를 용도에 맞게 정한다면 가상 스레드는 성능 개선 수단이 아니다"라고 정리했습니다.
> 그래서 최종 적용안은 **0단계(플랫폼 풀 재설정) + 세마포어 백프레셔 + 전용 dispatch 실행기**이며, 상세 내용은 §1-12에 있습니다.
> 1단계(가상 스레드)와 2단계(동기 스타일)는 적용하지 않았습니다.

### 1-11. 재검토: 배치와 가상 스레드는 의미가 있는가 (풀 크기를 제대로 정한다는 전제)

#### send 메서드를 바꾸면 달라지는가

firebase-admin 9.x의 전송 메서드는 결국 모두 "메시지 1건 = HTTP 요청 1건 = `ThreadManager` 실행기 스레드 1개 블로킹"으로 끝납니다.
따라서 **메서드를 바꿔도 동시성 상한은 달라지지 않습니다.** (9.5.0 소스로 확인했고, 9.4.0과 구조가 같습니다.)

| 메서드 | 내부 구현 | 동시성 상한 | 호출 스레드 |
|---|---|---|---|
| `send(Message)` | `sendOp(...).call()`: 호출 스레드가 직접 HTTP 요청 | 반복문으로 호출하면 **1** | 블로킹 |
| `sendAsync(Message)` | `sendOp(...).callAsync(app)`: 풀에 태스크 1개 제출 | 풀 크기 | 즉시 반환 |
| `sendEach(List)` | `sendEachOpAsync(...).get()` | 풀 크기 | 블로킹 (스레드 1개가 대기만 함) |
| `sendEachAsync(List)` (현재) | 메시지마다 `callAsync` 후 `allAsList` | 풀 크기 | 즉시 반환 |
| `sendEachForMulticast(Async)` | `getMessageList()` 로 변환 후 `sendEach(Async)` | 풀 크기 | 위와 동일. 모든 토큰에 같은 payload라서 회원별 `unread_count` 를 보낼 수 없음 |
| `sendAll` / `sendMulticast` (`@Deprecated`) | batch 엔드포인트로 최대 500건을 HTTP 요청 1건에 담음 | - | Google이 batch 전송 API를 2024년 6월 종료한 것으로 알려져 있어 사용 불가(종료 시점은 소스가 아닌 공지 기준) |
| 토픽 발송 | HTTP 요청 1건, 구독자 분배는 FCM 서버가 수행 | 해당 없음 | 토큰별 결과와 개인화를 포기해야 하므로 현재 Outbox 설계와 맞지 않음 |

#### 배치(400)의 의미

- **FCM 처리량 측면에서는 의미가 없습니다.** 400건을 넘겨도 HTTP 요청은 400번 나갑니다. 500은 SDK 한도(`checkArgument(size <= 500)`)일 뿐입니다.
- **DB 측면에서는 의미가 큽니다.** 배치는 사실상 DB 트랜잭션 단위입니다.

| 작업 | 1건 단위로 처리하면 | 배치 400이면 |
|---|---|---|
| `markBatchAsSendingAndSave` | 트랜잭션 10만 회 | 250회 |
| `processPushResult` | 트랜잭션 10만 회 + `push_clusters` 같은 행에 10만 번 UPDATE (행 락 경합) | 250회 |
| 콜백 실행 | 10만 회 | 250회 |

- 그래서 배치 크기는 **FCM이 아니라 DB 기준으로 정할 값**입니다 (bulk update 1회에 적당한 크기, SDK 한도 500 이하).
- 배치의 부작용
  1. **결과 반영이 가장 느린 1건에 맞춰집니다.** `allAsList` 가 끝나야 콜백이 실행되므로, 배치가 클수록 결과 반영 시점이 p99 지연에 좌우됩니다.
  2. **실패 범위가 배치 단위로 커집니다.** FCM 에러는 SDK가 건별로 `SendResponse.fromException` 으로 바꿔 주지만(소스로 확인),
     그 밖의 예외가 1건이라도 나면 `allAsList` 가 실패해 `onFailure` 가 400건 전체를 `RETRY_PENDING` 으로 바꿉니다(이미 성공한 건 포함).
     이번 리팩토링 범위에서는 제외했습니다.

#### 가상 스레드의 의미: 리틀의 법칙

```
필요 동시성 L = 목표 처리량 λ × 요청 1건의 소요 시간 W
```

FCM 쿼터가 초당 10,000건이므로 λ는 아무리 높여도 10,000건/초입니다.

| RTT | 쿼터를 다 채우는 데 필요한 동시성 |
|---|---|
| 50ms | 500 |
| 100ms | 1,000 |
| 200ms | 2,000 |

즉 **이 시스템의 동시성 상한은 스레드 기술이 아니라 FCM 쿼터가 정합니다.** 그 범위(수백~2,000)는 플랫폼 스레드로도 감당할 수 있습니다.

| 항목 | 플랫폼 스레드 1,000개 | 가상 스레드 1,000개 |
|---|---|---|
| 처리량 | 같음 | 같음 |
| 메모리 (스택 실사용, 추정) | 약 100~250MB | 약 수 MB~20MB |
| 동시성 제한 | 풀 크기가 곧 제한 | 세마포어를 따로 만들어야 함 |
| 메트릭 | `ExecutorServiceMetrics` 그대로 | 직접 만들어야 함 |
| 피닝 위험 (Java 21) | 없음 | 라이브러리마다 점검 필요 |

가상 스레드의 실질적 이득은 메모리 약 100~200MB 절약과 큐 크기를 정하지 않아도 되는 단순함 정도이고,
세마포어·메트릭·피닝 점검이라는 비용이 새로 생깁니다. 가상 스레드가 의미를 갖는 경우는 다음과 같습니다.

- 필요한 동시성이 수천~수만 단위일 때 (쿼터 제한이 없는 외부 API, RTT 1초 이상)
- 같은 서버에 블로킹 작업이 많아 풀을 각각 튜닝하는 대신 가상 스레드 + 세마포어로 통일하고 싶을 때
- 콜백 없이 동기 스타일 코드로 바꾸고 싶을 때 (성능이 아닌 가독성의 이득)

**정리:** 실제로 성능을 바꾸는 요소는 (1) 리틀의 법칙으로 정한 동시성 수치, (2) 큐 초과를 막는 백프레셔, (3) DB 기준의 배치 크기입니다.

### 1-12. 적용한 리팩토링: 튜닝 값과 그 이유

브랜치: `refactor/fcm-send-backpressure` (커밋하지 않음)

#### 풀 설정

| 풀 | 이전 (core / max / queue) | 변경 | 이유 |
|---|---|---|---|
| `fcm-default` (메시지 전송) | 32 / 128 / 50,000 | **200 / 200 / 2,000** + `allowCoreThreadTimeOut` | ①②③ |
| 처리 중 배치 상한 (신규 세마포어) | 없음 | **배치 3개 (메시지 1,200건)** | ④ |
| `fcm-callback` (결과 DB 반영) | 8 / 32 / 500 | **4 / 4 / 100** | ⑤ |
| `fcm-dispatch` (신규, 발송 루프) | 없음 | **2 / 2 / 100** | ⑥ |

**① 스레드 수 200: 리틀의 법칙**
목표를 "10만 건을 1분 안에 발송"으로 잡으면 λ ≈ 1,700건/초입니다. RTT 100ms를 가정하면 L ≈ 170이므로 여유를 두어 200으로 정했습니다.
RTT가 50ms로 줄어도 처리량은 4,000건/초로 FCM 쿼터(10,000건/초) 미만이라 `QUOTA_EXCEEDED` 가 생기지 않습니다.
스택 메모리 실사용량은 약 50MB로 추정합니다. RTT 실측값(§1-8)이 나오면 이 식에 다시 넣어 조정합니다.

**② core = max**
`ThreadPoolExecutor` 는 큐가 가득 차야 max까지 스레드를 늘리므로, 둘이 다르면 max는 사실상 동작하지 않습니다(§1-3).
발송은 평일 낮에 몰리는 작업이라 `allowCoreThreadTimeOut` 으로 유휴 시간에는 스레드를 반납합니다.

**③ 큐 2,000: 거절이 구조적으로 발생하지 않는 크기**
이 풀에 동시에 들어올 수 있는 메시지는 세마포어가 허용하는 발송분 1,200건(배치 3 × 400)과,
세마포어를 거치지 않는 `TokenValidationScheduler` 검증 배치 400건(동기, 한 번에 1개)입니다.
합계 1,600건이고 풀 용량은 스레드 200 + 큐 2,000 = 2,200건이라 넘칠 수 없습니다.
이전의 50,000은 "넘치지 않게 크게" 잡은 값이었고, 2,000은 "넘칠 수 없음을 계산으로 보장한" 값입니다.
이 조건은 기동 시 `FcmConfig` 에서 `max + queue >= (max-in-flight-batches + 1) × 500` 으로 검증합니다(500은 SDK의 호출당 최대 메시지 수).

**④ 처리 중 배치 3개**
허가는 배치 단위로, 배치의 가장 느린 1건까지 끝나고 콜백의 DB 반영이 끝난 뒤 반납됩니다.
배치가 1개면 꼬리 1건을 기다리는 동안 스레드 200개가 놀고, 메시지 수가 스레드 수보다 적으면 스레드를 다 쓰지 못합니다.
3개(1,200건)는 스레드 수의 6배라서 스레드가 놀지 않고, 앞 배치가 마무리되는 동안 다음 배치가 진행됩니다.

**⑤ 콜백 4개: 병목은 DB**
허가가 콜백 종료 후 반납되므로 동시에 실행되는 콜백은 최대 3개입니다. HikariCP 10개 중 웹 요청 몫을 남기기 위해 4개로 제한합니다.
DB 반영이 느려지면 허가 반납도 늦어져 발송 속도가 함께 줄어듭니다. 전송부터 DB 반영까지 한 흐름으로 백프레셔가 걸립니다.
콜백 실행이 거절되면 허가가 반납되지 않으므로, 기동 시 `max + queue >= max-in-flight-batches` 를 검증합니다.

**⑥ dispatch 2개: 웹훅 응답 지연 방지**
세마포어에서 기다리는 주체를 웹훅 Tomcat 스레드가 아니라 이 전용 스레드로 바꿉니다.
2개면 큰 클러스터 발송 중에도 다른 클러스터가 진행할 수 있습니다.
서버가 내려가거나 이 큐가 가득 차도 클러스터와 토큰은 이미 `PENDING` 으로 커밋되어 있으므로 폴링 릴레이가 복구합니다(Outbox 보장 유지).
폴링 릴레이의 재발송은 기존처럼 스케줄러 스레드(풀 4)가 세마포어를 기다리며 처리해, ShedLock을 잡은 동안 처리를 끝내는 방식을 유지합니다.

#### 왜 세마포어인가

| 대안 | 문제 |
|---|---|
| 큐를 크게 잡기 (이전 방식) | 큐는 "대기 중인 태스크"만 제한하고, 넘치면 배치 중간에서 거절되어 일부만 전송되는 상태가 생김(§1-4) |
| `CallerRunsPolicy` | 거절된 **메시지 1건**을 호출 스레드가 직접 블로킹 전송함. 배치 중간에서 발생하고, 호출 스레드가 전송 스레드 역할까지 떠안으며, 용량 설계 오류를 숨김 |
| 큐 크기만 줄이기 | 거절이 더 자주 발생할 뿐 해결이 아님 |
| Resilience4j Bulkhead | 개념은 같지만 의존성이 추가됨 |

세마포어를 선택한 이유는 다음과 같습니다.

1. **제한 범위가 "제출부터 콜백 DB 반영 종료까지"입니다.** 스레드 풀 큐는 실행 전 대기만 제한하지만, 세마포어는 전송·콜백·DB 반영 전체를 하나의 처리 단위로 묶습니다.
2. **배치 단위로 "전부 제출하거나, 아예 시작하지 않거나"가 됩니다.** 허가를 먼저 얻은 뒤 제출하므로 배치 중간 거절이 생기지 않습니다.
3. **거절 대신 대기합니다.** 상한에 닿으면 제출 스레드가 배치 시작 전에 깔끔하게 기다립니다.
4. **SDK가 소유한 실행기를 바꾸지 않고 바깥에서 제한할 수 있습니다.** 실행기는 `ThreadManager` 를 통해 SDK가 쓰고, 토큰 검증과도 공유됩니다.
5. **JDK 기본 기능**이라 의존성이 늘지 않습니다.
6. 부수 효과로 **허가를 얻은 직후에 `IN_PROGRESS` 를 표시**하므로 `processedTime` 이 실제 전송 시작 시각과 거의 같아져, 큐 대기 토큰이 stale로 오판되는 문제(§1-7의 3번)가 사라집니다.

#### 리뷰 반영: 토큰 선점(CAS)으로 중복 발송 차단

1차 리뷰에서 다음 문제가 지적되었습니다.

- `IN_PROGRESS` 표시를 허가 획득 뒤로 미루면, dispatch 큐나 세마포어에서 오래 기다린 토큰이 `PENDING` 상태로 10분을 넘길 수 있습니다.
- 그러면 폴링 릴레이가 그 토큰을 stale로 보고 재발송합니다.
- 뒤늦게 차례가 온 dispatch 스레드도 오래된 엔티티로 상태를 덮어쓰고 다시 보냅니다. 즉 중복 발송이 생깁니다.

이 문제를 다음 방식으로 막았습니다.

1. **발송 선점:** 허가를 얻은 직후, 배치 토큰 행을 `SELECT ... FOR UPDATE` 로 잠그고 **현재 상태가 기대 상태인 토큰만** `IN_PROGRESS` 로 바꿉니다. 기대 상태는 초기 발송이면 `PENDING`, 재발송이면 `RETRY_PENDING` 입니다. 메시지와 콜백은 선점한 토큰으로만 만듭니다.
2. **릴레이 보호:** `recoverStaleTokens` 도 상태를 바꾸기 전에 같은 방식으로 잠그고, **조회 시점의 상태가 그대로인 토큰만** 처리합니다.
3. **교착 방지:** 양쪽 모두 PK 오름차순 단일 쿼리로 잠가 잠금 순서를 하나로 통일했습니다.

결과적으로 같은 토큰을 dispatch와 릴레이가 동시에 집더라도, 먼저 잠근 쪽만 선점에 성공하고 다른 쪽은 그 토큰을 건너뜁니다.

그 밖의 반영 사항은 다음과 같습니다.

- **타임아웃:** FCM HTTP 타임아웃을 명시하고, 허가 대기에 300초 상한을 두었습니다. 넘기면 해당 클러스터를 중단하고 디스코드로 알립니다. 선점하지 않은 토큰은 상태가 그대로이므로 릴레이가 복구합니다.
- **종료 순서:** `@DependsOn` 으로 dispatch → default → callback 순서로 종료되게 해, 진행 중인 배치의 콜백이 먼저 종료된 callback 풀에 거절되지 않게 했습니다.
- **릴레이 중단 (2차 리뷰):** 허가 대기 초과나 인터럽트가 나면 `dispatchRetryTokens` 가 `false` 를 반환하고, 스케줄러는 남은 클러스터 처리를 멈춥니다.
  클러스터마다 300초씩 차단되거나 알림이 반복되는 일을 막기 위해서입니다.
- **허가 반납 보강 (2차 리뷰):** 콜백 등록 전에 어떤 예외(`Error` 포함)로 빠져나가도 `finally` 에서 허가를 반납합니다.

**알려진 한계 (ABA):** 선점은 상태 값만 비교합니다. ShedLock(`lockAtMostFor=9분`)이 만료되어 릴레이 두 개가 동시에 도는 경우, 다음과 같은 일이 생길 수 있습니다.

1. 먼저 시작한 릴레이가 조회해 둔 토큰이 그사이 "`RETRY_PENDING` → 발송 → 실패 → 다시 `RETRY_PENDING`" 을 거칩니다.
2. 상태 값이 처음과 같으므로 먼저 시작한 릴레이가 이 토큰을 다시 선점합니다.
3. 그 결과 중복 발송되고, `retry_count` 가 메모리에 남아 있던 이전 값으로 덮어써질 수 있습니다.

비교 대상에 `processed_time` 이나 `retry_count` 를 추가하면 막을 수 있지만, 이번 범위에서는 제외했습니다.

## 2. Transaction Outbox 레코드 누적과 정리 전략

### 2-1. 이 프로젝트에서 Outbox는 무엇인가

이 프로젝트는 별도의 `outbox` 테이블 없이, **`push_cluster_tokens` 테이블이 Outbox 역할**을 합니다.
`application.yaml` 의 주석도 `PushPollingPublisherScheduler` 를 "transaction outbox 복구 릴레이"로 설명합니다.


| 요소                                | 이 프로젝트의 대응                                                                                        |
| --------------------------------- | ------------------------------------------------------------------------------------------------- |
| Outbox 레코드                        | `push_cluster_tokens` 1행 = (알림 1건 × 기기 토큰 1개)                                                     |
| 이벤트 상태                            | `job_status`: `PENDING` → `IN_PROGRESS` → `SUCCESS` / `FAIL` / `RETRY_PENDING` / `PERMANENT_FAIL` |
| Message Relay (Polling Publisher) | `PushPollingPublisherScheduler` (평일 9\~21시, 5분 주기, ShedLock)                                      |
| 재시도 정책                            | `retry_count`, `retry_after` (지수 백오프 2^n분, 쿼터 초과 시 2배), 최대 3회                                     |
| 집계 결과                             | `push_clusters` 의 성공/실패/재시도 카운트 (`incrementCountsAndUpdateStatus`, `incrementRetryCounts`)        |


현재 코드에는 **종료 상태(`SUCCESS`, `FAIL`, `PERMANENT_FAIL`)에 도달한 행을 삭제하는 로직이 없습니다.**
따라서 행 수는 발송량에 비례해 단조 증가합니다.

### 2-2. 누적 속도 추정

```
하루 누적 행 수 = Σ (그날 생성된 클러스터 수 × 클러스터당 대상 토큰 수)
```

예시(가정값)를 넣어 보면 다음과 같습니다.


| 시나리오     | 클러스터/일 | 토큰/클러스터 | 일 누적 | 30일 누적 | 1년 누적  |
| -------- | ------ | ------- | ---- | ------ | ------ |
| 소규모      | 20     | 500     | 1만   | 30만    | 365만   |
| 중규모      | 30     | 3,000   | 9만   | 270만   | 3,285만 |
| 개강 시즌 피크 | 60     | 5,000   | 30만  | 900만   | -      |


"몇십만 건"은 소규모 기준으로 한 달, 중규모 기준으로 일주일이면 도달하는 규모입니다.
실제 누적 속도는 2-8의 SQL로 확인할 수 있습니다.

### 2-3. 수십만 건이 쌓였을 때 쿼리별 영향 분석

결론부터 말하면, **수십만 건은 MySQL(InnoDB)에게 큰 규모가 아니며, 인덱스가 의도대로 사용된다면
조회 성능은 전체 행 수에 거의 영향을 받지 않습니다.** 정리가 필요한 이유는 조회 성능보다는
저장 공간, 쓰기 증폭, 운영 작업(ALTER·백업), 개인정보 보존 기간 쪽에 더 가깝습니다.
다만 쿼리 하나는 구조적으로 점검이 필요합니다.

#### (1) `findAllByPushClusterWithMember` — 클러스터별 토큰 조회

```sql
SELECT ... FROM push_cluster_tokens pct JOIN members m ... WHERE pct.push_cluster_id = ?
```

- `idx_pct_push_cluster_id` 로 해당 클러스터 행만 읽습니다.
- 비용은 **그 클러스터의 토큰 수**에 비례하고, 테이블 전체 행 수에는 B-tree 깊이(log N)만큼만 영향을 받습니다.
- 수십만 → 수백만 건이 되어도 사실상 차이가 없습니다.

#### (2) `findRecoverableTokens` — 5분마다 도는 폴링 쿼리 (점검 필요)

```sql
SELECT ... FROM push_cluster_tokens pct
JOIN members m ... JOIN push_clusters pc ...
WHERE (pct.job_status = 'PENDING'       AND pct.request_time   <  :staleThreshold)
   OR (pct.job_status = 'IN_PROGRESS'   AND pct.processed_time <  :staleThreshold)
   OR (pct.job_status = 'RETRY_PENDING' AND pct.retry_after   <= :now AND pct.retry_count <= :max)
```

각 OR 분기마다 전용 인덱스가 준비되어 있습니다.


| 분기             | 인덱스                                                           | 사용 방식                                                                  |
| -------------- | ------------------------------------------------------------- | ---------------------------------------------------------------------- |
| PENDING        | `idx_pct_status_request (job_status, request_time)`           | `job_status` 등치 + `request_time` 범위                                    |
| IN\_PROGRESS   | `idx_pct_status_processed (job_status, processed_time)`       | `job_status` 등치 + `processed_time` 범위                                  |
| RETRY\_PENDING | `idx_pct_status_retry (job_status, retry_after, retry_count)` | `job_status` 등치 + `retry_after` 범위, `retry_count` 는 범위 뒤라서 ICP 필터로만 사용 |


**좋은 점:** 모든 인덱스가 `job_status` 로 시작하므로, 전체 행의 99% 이상을 차지하는 `SUCCESS` / `FAIL` 행은
인덱스 범위 탐색에서 아예 건드리지 않습니다. 즉 **쿼리 비용은 "복구 대상 행 수"에 비례하고 전체 행 수와는 거의 무관**합니다.

**점검이 필요한 점:**

1. **OR 조건과 옵티마이저 선택:** MySQL은 이 형태를 `index_merge (sort_union)` 로 처리할 수 있지만,
 통계가 부정확하거나 JOIN이 붙으면 **풀 테이블 스캔을 선택할 수도 있습니다.** 풀 스캔이 선택되면 비용이
 전체 행 수에 비례하게 되므로, 이 경우에만 "행이 쌓일수록 느려지는" 현상이 나타납니다.
 `EXPLAIN ANALYZE` 로 `type` 이 `index_merge` 인지 확인해야 합니다(2-8 참고).
2. **LIMIT이 없음:** 평소에는 복구 대상이 수십 건이지만, **FCM 장애가 30분 이어지면 그동안 발송한 토큰 전체가
 `RETRY_PENDING` 이 되어 한 번에 로드**됩니다. 수십만 건의 엔티티를 `member`, `pushCluster` 까지 JOIN FETCH 하면
 힙 사용량과 영속성 컨텍스트 비용이 급증합니다. **누적 행 수보다 이쪽이 실제 위험입니다.**
3. **트랜잭션 범위:** 조회된 토큰은 스케줄러가 클러스터별로 다시 배치 발송하는데, 이때 1장의 병목(동시성 32)과 겹치면
 다음 5분 주기 전에 끝나지 않을 수 있습니다. ShedLock이 중복 실행은 막지만, 처리 지연은 누적됩니다.

#### (3) 상태 전이 UPDATE — 쓰기 증폭

토큰 1행은 발송 과정에서 최소 2번 UPDATE됩니다(`IN_PROGRESS` → `SUCCESS`).
`job_status`, `processed_time` 이 바뀔 때마다 다음 인덱스 항목이 **삭제 후 재삽입**됩니다.


| 인덱스                        | UPDATE 시 갱신 여부                         |
| -------------------------- | -------------------------------------- |
| PK (clustered)             | 행 자체 갱신                                |
| `idx_pct_push_cluster_id`  | 변경 없음                                  |
| FK `member_id` 자동 인덱스      | 변경 없음                                  |
| `idx_pct_status_request`   | `job_status` 변경 → 갱신                   |
| `idx_pct_status_processed` | `job_status`, `processed_time` 변경 → 갱신 |
| `idx_pct_status_retry`     | `job_status` 변경 → 갱신                   |


즉 행 1개의 상태 변경마다 보조 인덱스 3개가 갱신됩니다. 이 비용은 **누적 행 수와는 거의 무관**하지만(B-tree 깊이만 영향),
인덱스 전체 크기가 InnoDB 버퍼 풀보다 커지는 시점부터는 디스크 I/O가 늘어나 체감 성능이 떨어집니다.
정리를 통해 테이블을 작게 유지하면 **인덱스 전체가 버퍼 풀에 머물게 되어** 이 위험을 예방할 수 있습니다.

#### (4) 운영 작업

- `ALTER TABLE` (컬럼 추가, 인덱스 추가)은 행 수에 비례하는 시간이 걸립니다. 수백만 건이 되면 온라인 DDL이라도 수 분 이상 걸리고,
이 프로젝트의 `create-indexes.sql` 처럼 인덱스를 재구성하는 작업이 부담스러워집니다.
- 백업/복원 시간, 로컬 환경으로 덤프를 받아 디버깅하는 시간도 함께 늘어납니다.
- `token_value` 는 기기를 식별할 수 있는 값이므로, **목적이 끝난 데이터를 무기한 보관하지 않는 것**이 개인정보 관점에서도 바람직합니다.

### 2-5. 정리(Cleanup) 전략 비교

#### 전제: 종료된 행을 지워도 되는가?

- **삭제 대상**: `SUCCESS`, `FAIL`, `PERMANENT_FAIL` 이면서 일정 기간(예: 30일)이 지난 행
- **삭제하면 안 되는 대상**: `PENDING`, `IN_PROGRESS`, `RETRY_PENDING` (폴링 릴레이가 처리해야 하는 행)
- **참조 무결성**: `push_cluster_tokens` 를 FK로 참조하는 테이블은 없습니다. 따라서 삭제해도 다른 테이블이 깨지지 않습니다.
- **집계 보존**: 클러스터 단위 성공/실패 수는 `push_clusters` 에 이미 누적되어 있으므로, 토큰 행을 지워도 통계는 남습니다.
사용자별 알림 이력은 `push_notifications` 가 따로 보관합니다.

#### 전략 비교


| 전략                            | 방식                                                                | 장점                                       | 단점                                                                                                                | 적합 규모        |
| ----------------------------- | ----------------------------------------------------------------- | ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | ------------ |

### 2-6. 권장안: 청크 단위 삭제 배치 스케줄러

수십만 건 규모에는 **전략 B(청크 DELETE) + 30일 보존**이 비용 대비 효과가 가장 좋습니다.
파티셔닝(D)은 FK 제거와 PK 변경을 요구하므로 수천만 건 규모가 되기 전까지는 과한 선택입니다.

**설계**


| 항목       | 값                                                  | 이유                                   |
| -------- | -------------------------------------------------- | ------------------------------------ |
| 실행 시각    | 매일 03:00                                           | 폴링 릴레이(평일 9\~21시)와 발송 트래픽을 피함        |
| 분산 락     | ShedLock `pushClusterTokenCleanup`                 | 다중 인스턴스에서 중복 실행 방지 (기존 관례와 동일)       |
| 토글       | `ajou.scheduler.enabled.push-token-cleanup` + 환경변수 | `push-polling` 토글과 같은 방식으로 재배포 없이 끄기 |
| 보존 기간    | 30일 (설정값)                                          | 사용자 문의·장애 분석에 필요한 기간                 |
| 청크 크기    | 2,000건                                             | 트랜잭션 1회가 수십 ms 안에 끝나는 크기             |
| 청크 간 휴식  | 100\~200ms                                         | 레플리카 지연, 버퍼 풀 경합 완화                  |
| 최대 실행 시간 | 10분                                                | 남은 행은 다음 날 이어서 처리                    |
| 관측       | 삭제 건수 카운터, 소요 시간 타이머, 디스코드 요약 알림                   | 기존 Micrometer·Discord 관례 활용          |


**PK 범위 기반 청크 삭제 (개념 SQL, 적용하지 않음)**

```sql
-- 1) 삭제 상한 PK를 한 번만 구한다 (보존 기간 이전 행 중 가장 큰 id)
SELECT MAX(id) INTO @upper
FROM push_cluster_tokens
WHERE request_time < NOW() - INTERVAL 30 DAY;

-- 2) 하한부터 청크 단위로 삭제한다 (PK 범위이므로 clustered index를 순차로 읽음)
DELETE FROM push_cluster_tokens
WHERE id >= @cursor AND id < @cursor + 2000 AND id <= @upper
  AND job_status IN ('SUCCESS', 'FAIL', 'PERMANENT_FAIL');
-- @cursor += 2000 후 반복, 청크마다 커밋
```

`id` 는 AUTO\_INCREMENT이고 `request_time` 과 거의 같은 순서로 증가하므로, PK 범위로 자르면
보조 인덱스를 거치지 않고 clustered index를 순서대로 읽어 가장 효율적으로 삭제할 수 있습니다.
`job_status` 조건 덕분에 30일이 지났는데도 종료되지 않은 행(이상 상태)은 남게 되며, 이런 행은 별도로 모니터링하면 됩니다.

**`LIMIT` 방식과 비교**

`DELETE ... WHERE request_time < ? AND job_status IN (...) LIMIT 2000` 도 가능하지만,
반복할수록 이미 삭제된 영역을 인덱스에서 다시 건너뛰어야 하고, 복제 환경에서 `LIMIT` 이 있는 DELETE는
statement 기반 복제 시 비결정적 경고가 발생할 수 있습니다. PK 범위 방식이 더 예측 가능합니다.

**소요 시간 추정**

- InnoDB에서 보조 인덱스 5개를 가진 행의 삭제 속도는 소형 인스턴스 기준 초당 5,000\~20,000건 정도로 가정합니다.
- 50만 건 초기 정리: 순수 삭제 25~~100초 + 청크 휴식(250청크 × 150ms ≈ 38초) → \*\*약 1~~2.5분\*\*
- 이후 일일 정리(중규모 9만 건/일): **약 10\~30초**

**삭제 후 공간 회수**

- InnoDB는 삭제한 공간을 내부적으로 재사용하므로, 매일 정리하면 테이블 크기가 일정 수준에서 안정됩니다.
- 이미 수백만 건이 쌓인 뒤 처음 정리하는 경우에만 `OPTIMIZE TABLE push_cluster_tokens` (온라인 DDL로 테이블 재구성)를
트래픽이 적은 시간에 1회 실행해 파일 크기를 줄이는 것을 검토합니다.

### 2-7. `findRecoverableTokens` 쿼리 개선안

정리 배치와 별개로, 폴링 쿼리 자체의 위험(2-3의 (2))을 줄이는 방법입니다.

1. **상한(LIMIT) 추가:** 한 주기에 최대 N건(예: 5,000건)만 가져오고, 나머지는 다음 주기에 처리합니다.
 FCM 장애 직후 수십만 건이 한 번에 로드되는 상황을 막습니다.
2. **OR 분기를 3개 쿼리로 분리:** 분기마다 전용 인덱스를 확실히 사용하도록 쿼리를 나누고 애플리케이션에서 합칩니다.
 옵티마이저가 풀 스캔을 고를 여지를 없애는 가장 확실한 방법입니다. (네이티브 쿼리로 `UNION ALL` 을 사용해도 됩니다.)
3. **ID만 먼저 조회 → 엔티티 로드:** 커버링 인덱스로 PK만 뽑은 뒤 필요한 만큼만 엔티티를 로드하면 JOIN FETCH 비용을 줄일 수 있습니다.
4. **인덱스 정리 검토:** `idx_pct_status_request` 와 `idx_pct_status_processed` 는 `job_status` 선두가 같으므로,
 stale 판정 기준을 `processed_time` 하나로 통일할 수 있다면 인덱스 1개를 줄여 쓰기 증폭을 낮출 수 있습니다.
 (현재 `PENDING` 행은 `processed_time` 이 NULL이므로 도메인 로직 변경이 필요합니다.)

### 2-8. 검증용 SQL 모음

```sql
-- 테이블 크기와 추정 행 수
SELECT table_rows,
       ROUND(data_length  / 1024 / 1024, 1) AS data_mb,
       ROUND(index_length / 1024 / 1024, 1) AS index_mb,
       ROUND(data_free    / 1024 / 1024, 1) AS free_mb
FROM information_schema.TABLES
WHERE table_schema = DATABASE() AND table_name = 'push_cluster_tokens';

-- 상태별 분포 (종료 상태 비율 확인)
SELECT job_status, COUNT(*) FROM push_cluster_tokens GROUP BY job_status;

-- 일별 누적 속도
SELECT DATE(request_time) AS d, COUNT(*) FROM push_cluster_tokens
GROUP BY d ORDER BY d DESC LIMIT 30;

-- 정리 대상 건수 (30일 경과 + 종료 상태)
SELECT COUNT(*) FROM push_cluster_tokens
WHERE request_time < NOW() - INTERVAL 30 DAY
  AND job_status IN ('SUCCESS', 'FAIL', 'PERMANENT_FAIL');

-- 폴링 쿼리 실행 계획 (type 이 index_merge 인지, rows 추정치가 작은지 확인)
EXPLAIN ANALYZE
SELECT pct.id FROM push_cluster_tokens pct
WHERE (pct.job_status = 'PENDING'       AND pct.request_time   <  NOW() - INTERVAL 10 MINUTE)
   OR (pct.job_status = 'IN_PROGRESS'   AND pct.processed_time <  NOW() - INTERVAL 10 MINUTE)
   OR (pct.job_status = 'RETRY_PENDING' AND pct.retry_after   <= NOW() AND pct.retry_count <= 3);

-- 인덱스 통계 갱신 (옵티마이저가 잘못된 계획을 고를 때)
ANALYZE TABLE push_cluster_tokens;
```

### 2-9. 결론

1. **수십만 건 자체는 조회 성능 문제를 거의 일으키지 않습니다.** 모든 폴링용 인덱스가 `job_status` 로 시작하기 때문에,
 쿼리 비용은 전체 행 수가 아니라 복구 대상 행 수에 비례합니다. 단, 옵티마이저가 OR 조건에서 풀 스캔을 고르지 않는지
 `EXPLAIN ANALYZE` 로 확인해야 합니다.
2. **실제 위험은 누적 행 수보다 `findRecoverableTokens` 에 LIMIT이 없다는 점**입니다. FCM 장애 직후에는 이 쿼리가
 수십만 건을 한 번에 로드할 수 있습니다.
3. **정리는 필요합니다.** 이유는 조회 속도보다 저장 공간·버퍼 풀 효율, 상태 전이 시의 인덱스 쓰기 비용,
 ALTER·백업 같은 운영 작업, 그리고 `token_value` 의 불필요한 장기 보관입니다.
4. **권장 방식은 "매일 03:00, 30일 보존, PK 범위 2,000건 청크 DELETE, ShedLock + 환경변수 토글"** 입니다.
 파티셔닝은 FK 제거와 PK 변경이 필요하므로 수천만 건 규모가 되었을 때 다시 검토합니다.
