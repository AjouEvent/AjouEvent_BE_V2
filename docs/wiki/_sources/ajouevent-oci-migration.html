개선 내역

A1 확보와 단일 인스턴스 완료
문제

Always Free 상태에서는 A1 한도가 0이라 1GB VM만 쓸 수 있었고, 사용률이 낮은 인스턴스가 회수될 위험이 있었습니다. 1GB VM 2대에 나눠 올리면 JVM 상한을 조이고 서비스 사이 통신을 사설 IP로 맞춰야 했습니다.

해결

PAYG로 업그레이드한 뒤 A1 4 OCPU / 24GB를 무료 한도 그대로 만들었습니다(첫 시도에 성공). 모든 컨테이너를 A1 한 대에 올리고, 예약 IP를 A1으로 옮겼습니다.

성과

앱 기동 17초, 컨테이너 전체 메모리 약 0.9GB로 24GB 중 대부분이 여유입니다. 서버 대수가 줄어 운영할 대상도 하나가 되었습니다. 스토리지는 150GB로 무료 200GB 안입니다.

OS 이미지 교체 완료
문제

Oracle Linux 9 기본 서비스(dnf 자동 갱신 597MB, PCP 수집기, cloud-agent)만으로 1GB가 바닥나서, 아무것도 올리지 않은 VM 2대가 모두 SSH 응답을 멈췄습니다.

해결

부트 볼륨만 Ubuntu 24.04 Minimal로 교체하고(VNIC · IP 유지), snap 기반 oracle-cloud-agent와 snapd를 제거했습니다.

성과

유휴 메모리 사용량 837MB → 310~344MB, 스왑 사용 628MB → 0. 두 VM 모두 SSH가 즉시 응답합니다.

스왑 · 커널 설정 완료
문제

1GB VM에서 메모리가 순간적으로 넘치면 OOM으로 컨테이너가 죽거나 VM 전체가 멈춥니다. 기본 스왑은 945MB였습니다.

해결

스왑 파일 4GB, vm.swappiness=10, vm.min_free_kbytes=32768, vfs_cache_pressure=50, 저널 100MB 제한, Docker 로그 10MB×3 로테이션. 컨테이너마다 mem_limit를 둡니다.

성과

메모리가 순간 초과해도 VM은 살아 있고, 한 컨테이너가 폭주하면 그 컨테이너만 재시작됩니다. JVM 힙이 스왑으로 밀려나는 일을 줄였습니다.

네트워크 접근 통제 완료
문제

아올다에서는 Redis 6379, Loki 3100, Grafana 3000, actuator 9090 등 9개 포트가 0.0.0.0에 열려 있었습니다.

해결

Security List는 SSH와 VCN 내부 통신만 허용하고, 80 · 443 · UDP 443은 NSG nsg-web로 VM 1에만 붙였습니다. 내부 포트는 사설 IP(10.0.0.x)나 127.0.0.1에만 바인딩하고, OS iptables도 같은 규칙으로 맞췄습니다.

성과

인터넷에 열린 포트 9개 → 3개. Grafana는 grafana.ajouevent.com으로 HTTPS를 거쳐서만 접근합니다.

고정 IP 확보 완료
문제

VM IP가 임시 IP였고, 예약 IP 한도 1개를 아무 백엔드도 없는 10Mbps 로드밸런서 oci-free-lb가 차지하고 있었습니다.

해결

쓰이지 않는 로드밸런서를 지우고 예약 IP 146.56.101.16을 VM 1에 붙였습니다. 10Mbps 고정 대역폭은 API 앞단에 두기에 부족해서 다시 만들지 않았습니다.

성과

예약 IP를 VM 1에서 A1으로 옮겨 붙였습니다. 서버를 바꿔도 DNS는 그대로이고, 앞으로 서버를 교체할 때도 같습니다.

MTU 정리 완료
문제

아올다 네트워크에 맞춰 Docker 브리지 MTU를 1450으로 고정해 두었습니다. OCI에서는 근거가 없는 값입니다.

해결

OCI VNIC은 9000(VCN 내부 점보 프레임)이고 인터넷 구간은 1500입니다. 새 compose와 docker-compose.local.yml에서 MTU 설정을 빼고 Docker 기본값 1500을 씁니다. 경로 MTU 탐지용 ICMP 3/4 규칙도 열었습니다.

성과

패킷이 쪼개지지 않는 표준 크기로 통신합니다. 아올다용 docker-compose.yml의 1450 설정은 전환이 끝날 때 파일째 지웁니다.

운영 비밀을 OCI Vault로 완료
문제

DB 비밀번호, JWT 키, Google 시크릿, Discord 웹훅이 아올다 서버의 .env 파일에만 평문으로 있었습니다. 서버가 사라지면 함께 사라지는 구조였습니다.

해결

값을 Vault 비밀로 옮겼습니다. VM은 인스턴스 주체로 Vault를 읽으므로 디스크에 OCI 인증 키를 두지 않습니다. DB 계정은 앱 · 크롤러 · 백업 용도로 나누고 비밀번호를 새로 만들었습니다.

성과

VM을 다시 만들어도 render-env.sh 한 번으로 설정이 복구됩니다. 크롤러 계정은 SELECT · INSERT · UPDATE · DELETE만, 백업 계정은 읽기만 가능합니다.

DB 백업 구성 완료
문제

지금까지는 RDS의 7일 자동 백업에만 의존했습니다. HeatWave 무료 DB는 백업 보존 기간을 1일에서 바꿀 수 없습니다(API가 거부).

해결

VM 2의 cron이 매일 04:30에 mysqldump → zstd 압축 → 쓰기 전용 PAR로 Object Storage에 올립니다. 수명 주기 정책이 14일 지난 덤프를 지웁니다.

성과

논리 백업 14일 치를 DB 밖에 보관합니다. VM에는 버킷 읽기 · 삭제 권한이 없어서, VM이 털려도 백업은 지워지지 않습니다.

HeatWave 설정 호환 · 복원 리허설 완료
문제

RDS는 sql_mode=NO_ENGINE_SUBSTITUTION(느슨한 모드)이고 HeatWave 기본값은 엄격한 모드입니다. 기존 무료 DB는 관리자 이름을 알 수 없어 접속할 수 없었고, HeatWave 비밀번호 정책은 특수문자를 요구했습니다.

해결

RDS와 같은 sql_mode 구성을 만들고, 기존 DB는 최종 백업을 남기고 삭제한 뒤 관리자 admin으로 같은 사설 IP에 다시 만들었습니다. DB 계정 비밀번호는 정책에 맞게 다시 만들어 Vault에 새 버전으로 넣었습니다.

성과

RDS 덤프(압축 21MB, 38초) → HeatWave 복원 85초. 테이블 17개, 공지 71,609 · 알림 889,446 · 이미지 88,163행이 RDS와 정확히 일치합니다. 전환 당일 DB 작업은 약 2분이면 끝납니다.

알림 발송 메시지 큐

문제

지금은 API 서버 안의 스레드 풀(전송 스레드 200개)이 FCM을 직접 호출합니다. 공지 웹훅이 몰리면 발송과 API 요청이 같은 JVM의 CPU · 메모리 · DB 커넥션(10개)을 나눠 씁니다.

해결

API는 outbox에 기록한 뒤 Redis Streams push-jobs에 발송 작업을 넣고 바로 응답합니다. Micro 1의 워커가 소비자 그룹으로 읽어 발송하고 XACK합니다. 실패한 작업은 XAUTOCLAIM으로 재시도하고, 5회 넘게 실패하면 push-jobs:dlq로 보냅니다.

기대 성과

발송량이 늘어도 API 응답 시간이 일정하게 유지됩니다. 워커만 늘려 발송 속도를 올릴 수 있습니다. 기존 outbox와 토큰 선점 로직이 중복 발송을 그대로 막습니다.

후보메모리판단
Redis Streams (추천)추가 없음이미 운영 중인 Redis를 씁니다. 소비자 그룹, ACK, 재시도, DLQ를 모두 구현할 수 있고 Sentinel 고가용성도 그대로 적용됩니다.
RabbitMQ약 150MBDLQ와 라우팅이 기본 기능이지만, 운영할 서버가 하나 더 생깁니다. 지금 발송량(FCM 월 5,209건)에는 과합니다.
Kafka1GB 이상이 규모에는 맞지 않습니다.

Caffeine + Redis 2단계 캐시 (Pub/Sub 무효화)

문제

API 레플리카가 2개가 되면 공지 목록 같은 읽기 요청이 매번 Redis까지 왕복합니다. 반대로 인스턴스마다 로컬 캐시만 두면, 한쪽에서 수정한 내용이 다른 쪽 캐시에 남습니다.

해결

L1은 인스턴스별 Caffeine(최대 1만 항목, TTL 30초), L2는 Redis(TTL 10분)입니다. 데이터가 바뀌면 Redis를 갱신한 뒤 cache:invalidate 채널에 키를 발행하고, 모든 인스턴스가 받아서 자기 L1을 지웁니다. Pub/Sub은 전달을 보장하지 않으므로, L1의 짧은 TTL을 안전장치로 둡니다.

기대 성과

자주 읽는 데이터는 JVM 메모리에서 바로 응답합니다. 인스턴스 사이에서 오래된 데이터가 보이는 시간은 최대 30초로 제한됩니다.

Redis 고가용성 (Sentinel)

Sentinel 3개(A1, push, watch)가 쿼럼 2로 마스터를 감시합니다. A1이 죽으면 Micro 1의 레플리카가 마스터로 승격되어 푸시 워커가 계속 동작합니다. 앱의 Redis 연결 설정을 Sentinel 방식(spring.data.redis.sentinel)으로 바꿔야 합니다.

진행 순서

  1. E2 Micro 2대로 이전 완료 (탭 1 · 2)
  2. A1 생성 · 예약 IP 이전 완료 → k3s 전환 (아래 ③ 상세 설계)
  3. 푸시 발송 워커 분리 + Redis Streams (아래 ② 상세 설계)
  4. Micro 2에 Gatus 외부 상태 점검
  5. 2단계 캐시와 Redis Sentinel (코드 작업)

보류 과제 상세 설계

이번 이전에서는 하지 않기로 한 과제 여섯 가지입니다. 실행할 때 그대로 따라 할 수 있게 목적, 구성, 설정값, 단계, 검증, 롤백 방법을 적었습니다. 추천 순서는 ① 알림 보관 배치 → ⑤ 이미지 캐시 프록시 → ⑥ 공지 본문 시각화 → ② 메시지 큐 → ③ k3s → ④ 이미지 미러링입니다. 앞의 것일수록 위험이 낮고, 사용자가 체감하는 효과가 바로 보입니다.

① 알림 보관 배치 (push_notifications 아카이브)

현황

2026-11-13 기준 889,608행, 약 370MB. 2025-03부터 월 3~6만 행이 쌓입니다. 인덱스는 (member_id, notification_type, notified_at), (member_id, is_read), (push_cluster_id)가 있습니다. HeatWave 50GB 기준으로 용량은 충분하지만, 회원별 목록 조회 범위가 계속 넓어집니다.

설계

매월 1일 04:00(KST)에 12개월이 지난 알림을 월 단위로 Object Storage archive/push_notifications/yyyy-mm.jsonl.zst에 내보내고, 내보낸 범위만 DB에서 지웁니다. ShedLock(@SchedulerLock(name="pushNotificationArchive"))으로 한 번만 실행되게 합니다.

효과

DB에는 최근 12개월(약 50~60만 행)만 남고, 지난 알림도 파일로 남아 필요하면 다시 넣을 수 있습니다. 공지(club_events, 13년 치 123MB)는 대상이 아닙니다.

# 설정 (application.yaml)
ajou:
  archive:
    push-notification:
      enabled: ${ARCHIVE_PUSH_NOTIFICATION_ENABLED:false}   # 처음에는 false로 배포 후 수동 1회 실행
      retention-months: 12
      chunk-size: 5000                                     # 한 번에 지우는 행 수 (잠금 시간 최소화)
      bucket-prefix: archive/push_notifications/

# 처리 순서 (월 1회, 대상 월마다)
1. SELECT id 범위 확인:  WHERE notified_at < :cutoffMonthEnd AND notified_at >= :cutoffMonthStart
2. id 오름차순으로 5,000행씩 읽어 JSON Lines로 압축 스트림에 기록 → Object Storage 업로드 (멀티파트)
3. 업로드한 객체의 행 수 = DB 행 수 확인 후에만 삭제 단계로 진행
4. DELETE FROM push_notifications WHERE id BETWEEN :from AND :to LIMIT 5000  (반복, 사이에 100ms 휴식)
5. 결과(월, 행 수, 객체 키, 소요 시간)를 Discord 운영 채널로 알림

  • 검증: 첫 실행은 enabled=false 상태에서 관리자 API로 1개월만 수동 실행합니다. 객체를 내려받아 행 수와 샘플 10건이 DB와 같은지 비교한 뒤 자동 실행을 켭니다.
  • 롤백: 지운 달의 .jsonl.zst를 내려받아 LOAD DATA 또는 INSERT 스크립트로 다시 넣습니다. 삭제는 업로드 검증 뒤에만 하므로 데이터 유실 경로가 없습니다.
  • 같이 정리할 것: 발송이 끝난 push_cluster_tokens(30만 행, 133MB)도 같은 배치로 12개월이 지난 클러스터 기준으로 정리합니다. 상태 PENDING · IN_PROGRESS · RETRY_PENDING인 행은 outbox 복구 대상이므로 제외합니다.

② 알림 발송 메시지 큐 (Redis Streams)

현황

웹훅 → PushCluster · push_cluster_tokens(outbox, 상태 PENDING) 저장 → 같은 JVM의 발송 루프(dispatch 풀 2개)가 FCM 전송 스레드 200개로 보냄. 복구는 PushPollingPublisherScheduler(평일 9~21시 5분마다, 지금은 환경 변수로 꺼짐)가 PENDING(오래됨) · IN_PROGRESS(오래됨) · RETRY_PENDING을 다시 보냅니다.

설계

outbox 저장까지는 그대로 두고, "발송 시작" 신호만 Redis Streams로 바꿉니다. API는 트랜잭션 커밋 뒤 XADD push:jobs로 클러스터 ID를 넣고 바로 응답합니다. 발송 워커(같은 이미지, SPRING_PROFILES_ACTIVE=prod,push-worker, 웹 포트 없음)가 소비자 그룹으로 읽어 발송하고 XACK합니다.

효과

발송이 몰려도 API 응답 시간과 DB 커넥션이 흔들리지 않습니다. 워커만 늘리면(Micro 1 추가 등) 발송 속도가 올라갑니다. 기존 토큰 선점 · 중복 차단 로직이 그대로 동작합니다.

# 메시지 (스트림 push:jobs, MAXLEN ~ 100000)
{ "clusterId": "19599", "type": "TOPIC|KEYWORD|RETRY", "enqueuedAt": "2026-11-13T14:40:33+09:00" }

# 소비자 그룹 / 워커
XGROUP CREATE push:jobs push-workers $ MKSTREAM
XREADGROUP GROUP push-workers worker-${HOSTNAME} COUNT 1 BLOCK 5000 STREAMS push:jobs >
→ 성공 시 XACK push:jobs push-workers <id>

# 재시도 · DLQ
- 1분마다 XAUTOCLAIM push:jobs push-workers worker-x 60000 0-0  (60초 넘게 ACK 안 된 메시지 회수)
- XPENDING 의 delivery count > 5 이면 push:jobs:dlq 로 옮기고 Discord 알림, 원본은 XACK

# 설정
ajou.push.queue.enabled: ${PUSH_QUEUE_ENABLED:false}   # false면 지금처럼 API JVM 안에서 바로 발송
ajou.push.queue.stream: push:jobs
ajou.push.queue.consumer-group: push-workers
  • 중복 방지: 메시지가 두 번 소비돼도 토큰 단위 상태 전이(PENDING → IN_PROGRESS 선점)가 있어 같은 토큰을 두 번 보내지 않습니다. 워커는 메시지를 "이 클러스터의 PENDING 토큰을 처리하라"는 신호로만 씁니다.
  • 안전망: Redis가 메시지를 잃어도 outbox(DB)에 PENDING이 남으므로, 지금의 폴링 릴레이를 하루 1회 저빈도로 켜 두면 복구됩니다.
  • 지표: XLEN push:jobs, 소비자 그룹 지연(XINFO GROUPS의 lag), DLQ 길이를 Micrometer 게이지로 내보내 Grafana 패널을 추가합니다.
  • 단계: (1) 큐 코드 + 기본값 off 배포 → (2) A1에서 워커 컨테이너 1개를 같이 띄우고 PUSH_QUEUE_ENABLED=true → (3) 일주일 관찰 → (4) 워커를 Micro 1로 옮김. 롤백은 환경 변수를 false로 바꾸는 것뿐입니다.
  • RabbitMQ · Kafka를 쓰지 않는 이유: 월 FCM 요청 약 5,200건 규모에서 별도 브로커(150MB~1GB+)를 운영할 이유가 없고, Redis는 이미 운영 중입니다.

③ k3s (A1 단일 노드)

현황

A1에서 Docker Compose로 운영합니다. 배포할 때 앱 컨테이너를 교체하는 동안(약 15~20초) Caddy가 요청을 최대 15초 기다리게 해 두었지만, 기동이 늦어지면 실패하는 요청이 생길 수 있습니다. 앱이 멈춰도 프로세스가 살아 있으면 Docker는 감지하지 못합니다.

설계

A1에 k3s(서버 1대, Traefik 끔)를 설치하고, Caddy를 그대로 인그레스로 씁니다(인증서 · 설정 재사용). 앱은 Deployment 레플리카 2개 + readiness/liveness 프로브로 롤링 배포합니다. Micro 2대는 클러스터에 넣지 않습니다.

효과

배포 중 실패 요청 0, 앱이 응답하지 않으면 자동 재시작, 서버 상태를 Git 매니페스트로 관리(Argo CD). k3s 자체 메모리는 약 500~600MB로, A1 여유 23GB에서 부담이 없습니다.

  • 크롤러: Deployment 레플리카 1개(strategy: Recreate)로 둡니다. 두 개가 뜨면 같은 공지를 두 번 보냅니다.
  • 단계: (1) 스케줄러 락 보강 배포 → (2) k3s 설치, Compose와 다른 포트로 전체 스택 띄워 검증 → (3) Caddy 업스트림을 k3s 서비스로 바꿔 전환 → (4) Compose 중지. 롤백은 Caddy 업스트림을 Compose 앱으로 되돌리는 것입니다.

⑥ 공지 본문 시각화 (원문 서식 보존 + 핵심 정보 카드)

현황
